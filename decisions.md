# Decision log — SchemeSetu

One entry per meaningful technical decision. This is interview preparation:
panels drill depth-first ("why this chunk size?"), and this file is where the
answers live. Template:

> **NNN — Title (date)**
> **Decision:** what was chosen. **Alternatives:** what else was considered.
> **Why:** the reason — with eval numbers once we have them. **Revisit when:** the trigger to reconsider.

---

**001 — Project renamed YojanaSathi → SchemeSetu (24 Aug 2026)**
**Decision:** SchemeSetu (*setu* = bridge). **Alternatives:** YojanaSathi (original), Patrata, SchemeScout.
**Why:** yojanasaathi.com already exists (a schemes news blog), and the Saathi/Sarathi/Mitra namespace is crowded with government apps. A bilingual name also mirrors a bilingual product. **Revisit when:** never — names are a one-way door once the repo is public.

**002 — Embedding model: all-MiniLM-L6-v2 now, BGE-M3 in Week 6 (24 Aug 2026)**
**Decision:** start with MiniLM (~90 MB, English-only, fast on CPU); the model name is a single config constant in `naive/rag.py`. **Alternatives:** BGE-M3 from day one (~2 GB, multilingual), API embeddings (Voyage/OpenAI — per-call cost).
**Why:** Weeks 1–5 are English-only per the PRD, so multilingual capacity buys nothing yet and the small model keeps the edit-run-learn loop fast. Making the model a config knob means the Week 6 swap is a one-line change we can A/B properly. **Revisit when:** Week 6 (Hindi), or if English retrieval quality plateaus below target.

**003 — Chunking: fixed ~800 chars with 150 overlap (24 Aug 2026)**
**Decision:** paragraph-packed fixed-size chunks as the Week-1 baseline. **Alternatives:** recursive splitting, structure-aware (by headings) — both scheduled for Week 2.
**Why:** simplest possible baseline; its eval numbers are the yardstick the Week-2 strategies must beat. Chosen by simplicity, not by measurement — that's acceptable only for a baseline. **Revisit when:** Week 2, by dev-set numbers.

**004 — Corpus acquisition: browser-rendered myScheme pages + official PDFs (27 Aug 2026)**
**Decision:** extract scheme text from myscheme.gov.in via a real browser (the site is a JavaScript app whose sections load client-side, sometimes flakily), and download guideline PDFs where reachable; every document gets a provenance header and a row in `data/registry.csv`. **Alternatives:** direct portal downloads (pmkisan.gov.in and pmayg.nic.in timed out from this network; agriwelfare.gov.in blocks non-browser clients with 403), the myScheme private API (undocumented, needs a scraped key — rejected), third-party mirrors like InstaPDF/Scribd (weak provenance — last resort only).
**Why:** corpus authenticity and traceability beat convenience; the registry records exactly what was fetched, from where, when, and how complete it is (three pages captured partial sections — recorded, not hidden). Raw corpus files stay out of git (large, redistributable from source); the registry IS committed, so anyone can rebuild the corpus. **Revisit when:** portals become reachable (fetch the canonical guideline PDFs), or corpus needs Hindi documents (Week 6).

**005 — PDF parsing: pypdf (27 Aug 2026)**
**Decision:** `pypdf` for PDF→text, with per-page thin-page warnings. **Alternatives:** PyMuPDF (better layout handling, AGPL license), Docling (best tables/structure, heavy), OCR pipelines (only needed for scanned documents).
**Why:** pure-Python, tiny, sufficient for text-first PDFs like our current guidelines; the parse report tells us when a document needs a heavier tool instead of failing silently. **Revisit when:** a critical document shows thin-page warnings (scanned) or mangled tables — that's the trigger to bring in Docling per PRD §8.

**006 — Chunking: structure-aware with [Title › Section] labels wins (27 Aug 2026)**
**Decision:** default chunker is `structure` (split at markdown headings, keep sections whole, label every chunk with its document title and section; provenance boilerplate stripped by `clean_text` before chunking). **Alternatives raced** (evals/compare_chunkers.py, 4 configs, identical corpus/embedder/questions): fixed-raw (Week-1 replica), fixed-clean, recursive, structure.
**Why — the numbers:** dev MRR@10: fixed 0.929, recursive 0.905, structure **1.000** (only config to fix the NMMSS-vs-PMS-SC scholarship confusion — the label tells the embedding which scheme a chunk belongs to). Mid-word chunk starts: ~65% (fixed/recursive) → **0%** (structure). Trap-vs-answerable top-1 gap: widest under structure (0.33 vs 0.66 on dev). Notable negative result worth remembering: *smarter split boundaries alone (recursive) slightly hurt ranking; the win came from context labels, not prettier cuts.* Cleaning alone changed no dev metric but re-ranked golden questions (see 007). **Revisit when:** corpus gains heading-less document types (label falls back to title only), or Week-4 reranking changes what precision@k needs.

**007 — Gold labels are maintained artifacts, not one-time annotations (27 Aug 2026)**
**Decision:** whenever the corpus grows, re-check (a) every trap — an answer entering the corpus un-traps it (happened with PM-JAY, dev-004), and (b) every `gold_doc_ids` list — a new document that also contains an answer must be added as gold (happened with pm_kisan_faq.txt: cleaning let it outrank the labelled golds, making correct retrieval score as a miss — golden MRR "fell" to 0.750 until the label was fixed).
**Why:** eval numbers are only as true as their answer key; a stale key turns real improvements into phantom regressions and vice versa. This is label maintenance, not tuning — the questions and answers never changed. **Revisit when:** the golden set is frozen — after freezing, label corrections get logged here rather than silently edited.

**008 — BM25 built from scratch; Qdrant deferred to the deploy phase (28 Aug 2026)**
**Decision:** implement BM25 ourselves (`naive/bm25.py`, ~60 lines: TF, smoothed IDF, k1 saturation, length normalisation) instead of the PRD's `rank_bm25` package, and keep retrieval in-process instead of adopting Qdrant this week. **Alternatives:** rank_bm25 (same algorithm, one pip install — the production swap stays trivial), Qdrant now (Docker or cloud signup).
**Why:** the project's learning rule — build the algorithm once by hand before using the library — and this one is small enough to hand-build in an afternoon while being permanent interview material (explain IDF? saturation? we wrote them). Qdrant solves scale/persistence/filtering, none of which binds at 116 chunks; it earns its keep at deployment (Week 7), where its free cloud tier also matters. **Revisit when:** corpus outgrows brute force, metadata filtering (FR-3.3) is needed, or deploy week arrives.

**009 — Retrieval: hybrid (dense + BM25, RRF fusion) is the default (28 Aug 2026)**
**Decision:** `RETRIEVAL_MODE = "hybrid"` — both retrievers run, results fused by Reciprocal Rank Fusion (1/(60+rank), ranks not scores, because cosine and BM25 scales are incomparable). **Alternatives raced** on the hardened 16-question dev v2 (the old dev set was saturated at 1.00 — an exam nothing can fail teaches nothing): dense hit@5 0.93 / MRR 0.940; bm25 0.93 / 0.929; hybrid **1.00** / 0.917.
**Why:** hit@5 is the north-star recall metric — a gold document absent from the top-5 is unrecoverable by anything downstream, while a rank-2/3 result is recoverable. The per-question matrix confirmed complementary failures: BM25 could not find the zero-word-overlap paraphrase ("my wife is expecting..." → maternity benefit, rank >10); dense wandered on the keyword-ish synthesis query ("transfer money directly into bank account", rank 6); hybrid held every question in top-5. Accepted cost: MRR dipped 0.940 → 0.917 (fusion dilutes single-mode wins) — that is deliberately the Week-4 reranker's job, giving the classic two-stage architecture: **hybrid maximises recall into a candidate pool; the reranker restores precision at the top**. Honest surprise worth quoting: dense handled name/abbreviation queries fine *because Week 2's [Title › Section] labels already put names into every chunk* — one improvement pre-empted part of the next. **Revisit when:** the reranker lands (re-tune the pool size), or corpus growth changes the balance.

**010 — Reranker: cross-encoder ms-marco-MiniLM-L-6-v2 over hybrid's top-20 (28 Aug 2026)**
**Decision:** two-stage retrieval completed — hybrid nominates 20 candidates (recall), a cross-encoder re-scores each (query, chunk) pair and the top 5 by that score ship (precision). **Alternatives:** BAAI/bge-reranker-v2-m3 (PRD's pick — multilingual but ~2.3 GB; deferred to Week 6's multilingual swap, same play as the embedder in 002), no reranker (keep fused ranks), LLM-as-reranker (costs per query).
**Why — the numbers:** dev MRR@10 0.917 → **1.000**; both fusion-diluted questions (dev-012 rank 3, dev-013 rank 2) promoted to rank 1; golden set unchanged at 1.000. The conceptual line for interviews: a bi-encoder embeds query and chunks *independently* (fast, approximate — scalable to millions), a cross-encoder reads the *pair* together (precise, unscalable) — so you cascade them: recall first, precision second. **Revisit when:** Week 6 (multilingual reranker), or latency budgets tighten (pool size is the lever).

**011 — Refusal: hard threshold 1.5 on the top-1 rerank score (28 Aug 2026)**
**Decision:** refuse to generate when the best reranked chunk scores below **1.5**. Method: collected top-1 rerank scores on the dev set — answerable [-6.07, then +3.10 … +8.29], traps [-7.69, +0.48] — and placed the threshold inside the (0.48, 3.10) gap, biased low to favour answering. Result: trap refusal 2/2 (dev) + 1/1 (golden), false refusal 1/14 = 0.07 — both PRD §5 targets met.
**Two findings worth remembering:** (1) the near-miss trap "PMAY *Urban*" scores **+0.48** because PMAY-*Gramin* chunks are genuinely topically relevant — semantic near-misses defeat naive cosine thresholds and are exactly why the threshold sits on cross-encoder scores with a margin. (2) The one false refusal, dev-012 ("my wife is expecting our first baby…"), retrieves the CORRECT document at rank 1 yet scores -6.07 — ms-marco's absolute scores are unreliable for conversational paraphrases with zero lexical overlap, even when its *ranking* is right. **Mitigation is Week 5's agent:** on a below-threshold score, rewrite the query ("maternity benefit for pregnant women") and retry once before refusing — turning a hard threshold into a graded loop. **Caveat:** 2 dev traps is a tiny tuning sample; the golden set needs its full 10 traps before this threshold is trustworthy (see evals/README composition). **Revisit when:** golden traps exist, or the Week-6 reranker swap changes the score scale (threshold must be re-tuned — it is model-specific).

**012 — Agent: LangGraph state machine; reranker score doubles as the CRAG-lite evidence grade (29 Aug 2026)**
**Decision:** the agent is a LangGraph `StateGraph` (classify → retrieve → grade → generate → verify, with refusal exits), adopted because this is exactly where a framework earns its keep: conditional edges, cycles (rewrite-and-retry, regenerate-once), and checkpointing support that a hand-rolled pipeline would reinvent badly. Three sub-decisions: (a) **LLM calls stay on the raw Anthropic SDK** behind a one-method seam (`LLM.complete`) — no langchain-anthropic layer; fewer dependencies, and the seam lets tests inject a scripted LLM so the graph's routing is provable offline against the REAL index (18/18 tests, including the dev-012 rescue). (b) **Evidence grading = the Week-4 rerank score** against the tuned threshold — the PRD's "CRAG-lite grade" without an extra LLM call per question; CRAG's LLM-grader is the upgrade path if golden-set data ever shows the score misgrading. (c) **Grounding verification is an LLM self-check** (PASS/FAIL fact-checker over the exact context), one regeneration allowed, then refusal — hallucination control as a *node*, not a hope.
**Deferred:** FR-5.2 conversation memory (checkpointed message history threaded into prompts) — `build_graph` accepts a checkpointer already; the CLI deliberately does not advertise memory it doesn't yet have. **Revisit when:** live LLM eval runs (needs API key) — trap-refusal ≥ 0.90 on golden traps is the Week-5 exit criterion still open.

**013 — Cost-free operation: provider-agnostic LLM seam with free-tier defaults (29 Aug 2026)**
**Decision:** all LLM calls route through `agent/llm.py`, which auto-selects among Anthropic (PRD default, paid), Groq / Gemini / Cerebras free tiers, or a local Ollama — whichever is configured. Hosted free providers share one ~20-line httpx client because they all speak the OpenAI-compatible `/chat/completions` wire format (the industry's de-facto standard); Anthropic keeps its native client. Zero new dependencies (httpx ships with the anthropic SDK).
**Why:** the project must run at ₹0 — every other component was already local/free (embeddings, reranker, BM25, CI, hosting), leaving LLM calls as the only paid piece. The Week-5 seam (012) made this a configuration concern rather than a rewrite, which is itself the lesson: abstractions are judged by the changes they make cheap. **Trade-offs recorded honestly:** free tiers are rate-limited (eval runs may need throttling), provider model catalogs drift (defaults here will age — `LLM_MODEL` overrides without a code change), and the judge-vs-generator separation (§8 of the PRD) now maps to *two different free providers* (e.g. generate on Groq, judge on Gemini). **Revisit when:** rate limits bite during the 55-question eval runs (add backoff), or deployment (Week 7) needs a latency/quality decision.
**014 — Agent-level evals, layered refusal, and resilient judging (29 Aug 2026)**
**Decision:** the agent is evaluated end-to-end (`evals/run_agent_eval.py`) — every question through the full graph, refusal correctness + cited-gold + faithfulness by an LLM judge that is *independent of the generator* (different provider; documented fallback: same provider, different model, when a free-tier daily quota kills the primary judge mid-run).
**What the first run caught — the reason agent-level evals exist:** component metrics composed non-linearly. The rewrite loop (built to rescue paraphrase false-refusals) also *laundered traps*: rewriting "Mudra interest rate" into scheme vocabulary pushed near-miss chunks over the retrieval threshold. Retrieval-level eval scored trap refusal 3/3; agent-level scored 1/3. Inspection showed the model was actually refusing in prose (grounding held!) while the graph decorated the refusal with a Sources footer — a measurement/behavior mismatch. **Fix — refusal as layers, each machine-readable:** (1) retrieval threshold (topical closeness), (2) generation replies exactly `NO_ANSWER` when close-but-empty context lacks the answer → routed to a true refusal, (3) verifier fails answers that address a different scheme than asked. Post-fix: trap refusal 3/3, false refusal 0/16, faithfulness 16/16 at the agent level.
**Also learned:** (a) LLM rewrites are nondeterministic — identical questions take different graph paths run to run; layered refusal makes the variance harmless, but single-run evals are noisy (report caveats). (b) HTTP 429 has two species — per-minute ("slow down", retry) and daily quota ("come back tomorrow", fail fast so fallbacks engage); the backoff now distinguishes them, and the judge chain drops a dead judge for the rest of the run. **Revisit when:** the golden set reaches full size (re-run everything), or judge disagreement needs arbitration (add human spot-checks per PRD §9's 20% rule).

**015 — Multilingual retrieval: BGE-M3 cross-lingual beats translate-then-retrieve (28 Aug 2026)**
**Decision:** `EMBED_MODEL = BAAI/bge-m3` — the Week-6 swap that decision 002 scheduled, executed with A/B evidence (`evals/compare_embedders.py`, dense-only to isolate the embedder). **The numbers (Hindi dev questions, hit@5/MRR):** MiniLM 0.75/0.458 (English-only model limps), BM25 0.00/0.000 (keyword search shares zero tokens across languages — the deliberate control), translate-then-retrieve 1.00/0.875 (works, but adds an LLM call, latency and a failure point per query, and ranks worse), **BGE-M3 1.00/1.000** (Hindi and English meaning share one vector space; Hindi queries hit English documents directly). **The check most people skip:** BGE on the *English* set — 1.00/0.943 vs MiniLM's 0.93/0.940, i.e. the swap also fixed an English miss. A swap that wins one language by losing another is a trade; this was an upgrade. Cost: 2.3 GB model, ~10× slower indexing (still under 2 minutes for our corpus), 1024-dim vectors. **Revisit when:** corpus scales enough that embedding latency matters (then consider serving BGE-M3 via an API or quantised).

**016 — Reranker follows the embedder; threshold re-tuned for the new scale (28 Aug 2026)**
**Decision:** `RERANK_MODEL = BAAI/bge-reranker-v2-m3` (an English-only cross-encoder would garbage-score Hindi pairs and break refusal), and `REFUSAL_THRESHOLD` re-tuned 1.5 → **0.40**: the new model outputs 0..1 scores, so the old logit-scale threshold would have refused *every* question — exactly the failure decision 011 warned about ("threshold is model-specific; re-tune on swap"). New dev distributions: traps ≤ 0.14, answerable cluster ≥ 0.65, two conversational/synthesis stragglers at ~0.01–0.02 below threshold — by design left to the agent's rewrite loop, which demonstrably rescues them (dev-012 EN and dev-019 HI both verified live). Cross-lingual reranking confirmed: all four Hindi questions promoted to rank 1 (one from rank 7). **Live validation of the layered defense:** the Hindi drone trap was laundered to 0.93 by the rewrite, and the generation-level NO_ANSWER layer (014) still refused it — Week 5's fix protecting Week 6's feature. **Revisit when:** golden-set traps reach full strength (re-verify the 0.40 gap holds at scale).

**Postscript to 013 (29 Aug 2026):** the drift caveat fired the same day — Groq had already retired the entire Llama-3.3 line (404 model_not_found on first live call). Diagnosed by listing `GET /models` with the live key; defaults now `openai/gpt-oss-120b` (Groq) and `gemini-2.5-flash` (Gemini), with the verification date pinned in a comment. The debugging recipe is the durable lesson: 404 on a correct endpoint → suspect the model id → ask the provider's catalog, never guess.
